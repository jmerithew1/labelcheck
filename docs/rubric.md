# LabelCheck Requirements Rubric

Every requirement extracted from [brief.md](brief.md), tracked with evidence. Vocabulary: **MET** (with evidence), **PARTIAL**, **MISSING**, **N/A-documented**. A claim only moves to MET with a file, test, measured number, or URL attached — never on "code written."

Verification points: spec approval (done), post-build final gate (done), pre-submit audit loop (done 2026-08-11): round 1 — 5 independent auditor lanes (clean-clone build, core claims, live app, brief-coverage adversary, docs-drift), 0 blockers / 9 minors, all fixed; round 2 — 4 lanes re-verifying live production behavior + docs, 0 blockers / 3 doc-accuracy minors, all fixed; round 3 — scoped re-check of the round-2 fixes found 3 residual doc findings (stale claims duplicated in the generator and decisions log; an unbacked latency number), fixed; round 4 — final re-check of the round-3 fixes, clean (loop exit). **Ship-readiness sweep 2026-08-12** (4 lanes over the full feature set against production — API + error handling, batch UI, single-check UI, repo/docs): 3 blockers (native image-drag killed drag-to-pan; two stale doc counts) and 6 minors, all fixed and re-verified; the changes it covered are the 2026-08-12 additions (attention-only bold strip, undo, agent ruling, hover magnifier, honest row status, opt-in bold pass over 60 rows, distinct demo artwork). **Three further passes since:** an out-of-sample sweep 2026-08-13 (real TTB corpus, batch and single page driven as a user, which produced the band-accuracy finding and the deskew work); an owner walkthrough 2026-08-14 that reported eight UI defects, all fixed and re-verified on the deployed URL; and a documentation audit 2026-08-14 reading every tracked doc against the evidence file it cites — which found a wrong per-label latency figure, two docs leaning on a claim this rubric had already demoted, and two measurement harnesses hardcoded to one machine's paths so a fresh clone could not run them. All fixed.

Validated against **200 harvested real TTB COLA labels, 156 of them scored** ([real-labels.json](real-labels.json)), which found and fixed two real defects — missing spaces after "(1)" treated as a wording deviation, and transcription running past the statement into an adjacent declaration; live: word-swap label fails with deviation named
- **C8 — MET** `GOVERNMENT WARNING` ALL-CAPS check; title case = hard fail — same module + test; live: title-case sample fails with §16.22(a)(2) citation
- **C9 — MET for wording and ALL CAPS (deterministic); bold is confidence-gated** — the plain-English version of the accuracy argument, for anyone asking "can't a model just tell?", is [approach.md § How accurate is the bold check?](approach.md#how-accurate-is-the-bold-check). These are two different kinds of check, so they are stated separately rather than collapsed into one verdict. Word-for-word and ALL-CAPS are deterministic string comparisons over a transcription and may hard-fail. **Bold cannot be, so it never fails a label**: it auto-verifies only where pixel measurement and model advisory agree, and routes everything else to a human. Multi-signal gate (stroke width + ink density + size sanity + Sonnet judgment) validated in a 3-round spike loop at zero confident mistakes — but on only **14 auto-resolved validation decisions**, which by the rule of three is consistent with a true error rate as high as ~21%, so the scale re-score below is the load-bearing evidence, not the spike. Re-scored against 160 non-bold samples across 4 templates × 40 degradations: **3 silent misses (1.9%) worst-case through the shipped gate**, with 7 caught by measurement alone and 150 routed to a person. Worst-case because it assumes the model wrongly answers "bold" on all 160. All three leaks are `glare2`/`noise1` — degradation that physically thickens strokes, i.e. the predicted failure mode rather than a surprise. **1.9% is not zero**: the defensible claim is that a non-bold label is very unlikely to reach a green check, not that it cannot. The re-score harness imports the shipped gate directly ([bold-gate-rescore.mjs L33](../samples/tools/bold-gate-rescore.mjs#L33)) instead of restating its thresholds — a local copy silently fell out of sync the moment the gate gained a resolution floor, and would have gone on reporting against a gate that no longer existed ([bold-gate-rescore.json](bold-gate-rescore.json)). Versus **47 of 160 (29%)** for the raw model advisory alone — both measured on the same 160 samples — the measurement is what makes the difference, and anything it cannot resolve shows amber, never a green check. (That 47/160 advisory baseline is computed from the non-bold rows of [robustness-matrix.json](robustness-matrix.json), the corpus carrying the raw server advisory — this line previously miscited the 104-row [bold-multisignal-r2.json](bold-multisignal-r2.json) tuning run, which contains no such figure.) confident-bold auto-resolves ("verified by measurement"), confident-not-bold escalates to Needs review, inconclusive keeps the human glance via the **Confirm bold** strip (crops grid, Accept/Reject, CSV `bold_check` column: agent_verified / agent_flagged / auto_verified / auto_flagged / unconfirmed); live sample batch: a majority of bold-eligible rows auto-resolve and the rest go to a human glance — the exact split varies run to run because the stroke-weight signal is re-judged each time, and no run log is committed, so treat the observed "roughly 7 of 11" as an anecdote rather than evidence; gate logic unit-tested (`lib/compare/boldGate.ts`); the §16.22(a) **body-not-bold** rule is also checked now (advisory, routes to review — 255 tests)
- **C10 — MET** Fuzzy fields, case/punct = MATCH surfaced: `STONE'S THROW` = `Stone's Throw` — [lib/compare/fields.ts](../lib/compare/fields.ts) + test; live: batch case-diff rows land clean-with-note (case-diff label also downloadable for single check)
- **C11 — MET** Diffs/confidence visible; agent decides — char-level diffs ([components/CharDiff.tsx](../components/CharDiff.tsx)), similarity %, verdict language; only the warning uses FAIL language. **Both** surfaces now carry an audit trail ([components/AuditTrail.tsx](../components/AuditTrail.tsx)): the batch panel has had one since it shipped, and the single check gained one on 2026-08-14 — it had none, so the same label was traceable through a batch and opaque when checked by hand. Collapsed at the foot of the result, and forced open in the printed copy, because a filed record that omits how the result was produced is the one thing an audit trail exists to prevent. Verified live: real filename and size, the measured read time, the named readers, and the *Second opinion* entry appearing on a genuine warning failure
- **C12 — MET** Bottler name/address optional field — form + engine, skipped-when-blank shown
- **C13 — MET** Country of origin optional field — same
- **C14 — MET (measured under degradation)** Jenny's evasion tactics all countered — and tested for survival under 40 degradation conditions each ([robustness-matrix.json](robustness-matrix.json)): text-based evasions (word swap, word drop, punctuation drift, title-case prefix) are caught in **635 of 640 samples (99.2%)** — that denominator counts only the 16 text-defect labels, deliberately excluding the 4 bold-only labels, because crediting bold misses to a text-evasion score would inflate it. Overall violation catch across all 800 samples is **739 of 800 (92.4%)**; the gap is the bold advisory, see C9. Jenny's evasion tactics all countered — *different wording*: exact canonical comparison + character diff (C7); *smaller font*: extractor reports warning size relative to the label, surfaces an advisory even when text is exact ([lib/vision/contract.ts](../lib/vision/contract.ts) `warning_text_size`; physical mm/characters-per-inch documented as not machine-checkable from an image, [approach.md](approach.md) §limitations); *buried in tiny text*: full-label transcription + tri-state presence — a warning anywhere on the label is found or its absence/illegibility flagged

### Performance
- **P1 — MET at the median; the tail is over the bar and is not rounded away.** **Distribution measured 2026-08-14, n=30 on the deployed app** ([latency-p95.json](latency-p95.json)) — the first sample here large enough for a percentile to mean anything, since the n=6 and n=10 runs below can only report a median and a maximum: **p50 4.58s · p90 5.36s · p95 5.48s · max 5.67s · 7 of 30 (23%) over five seconds.** Sequential single checks rotating four labels, `async_confirm=1` so the figure is time-to-verdict-on-screen, round-tripped from a developer machine so it carries upload and public-internet latency an agent on TTB's LAN would not. So the defensible claim is precise: the brief's ~5s is met **at the median**, and roughly a quarter of checks land above it, none of them near the 30-40s that killed the prior vendor pilot. **The tail is one image, not a load tail.** Broken down by label, all 7 of the over-5s checks are the same file — `clean-match--glare2` (n=8, median 5.28s, 7 over); `batch-vodka--shadow2` (n=7, median 4.75s), `harbor-gin--dark3` (n=8, median 4.00s) and `title-case-prefix--cast2` (n=7, median 3.90s) never crossed five seconds once between them. So p95 does not mean "one check in twenty is slow"; it means one of the four rotated images is consistently ~1.3s slower than the rest and the round-robin samples it a quarter of the time. Client and network overhead is a median of **274ms** (max 474ms) across all 30, so the difference is time inside the vision model — a glare-heavy photograph costs it more — rather than transport or browser work. Two consequences worth stating: the percentile is sensitive to the mix of images in the sample, so a corpus with fewer glare photos would report a lower p95 and a corpus of nothing but them a higher one; and the honest headline is that a **typical label answers in about 4.5 seconds while a badly lit one takes about 5.3**, which is a statement an agent can act on in a way that a percentile is not. Current build, re-measured after the deskew shipped: **p50 4.06s, worst 5.32s** (n=6, [post-deskew-latency.json](post-deskew-latency.json)) — one run of six crossed ~5s, and n=6 undersamples the tail rather than characterising it. The defensible claim is that the *median* label answers in about four seconds, not that five is a ceiling. The earlier pre-deskew run ([measured-performance.json](measured-performance.json), 2026-08-11) read **p50 4.3s, worst 4.5s across n=6 successful runs** and is kept for history — note that one is also worst-of-successful: `scripts/measure.ts` excludes non-OK responses, and [approach.md](approach.md) §limitations 6 records a cold start at 9.3s, a warm worst at 9.6s, and one run that never returned inside 45s. The ~5s figure is a median, not a ceiling; warning-*failing* labels also answer in **~4.0s** (measured live) — their second confirming reading runs asynchronously via `/api/confirm` (measured 5.4s) and updates the warning row in place, so the false-rejection guard (U4) costs no waiting; batch rows keep the blocking pass (~8s/row, absorbed by the batch wall-clock) — raw timings in [measured-performance.json](measured-performance.json). **Out-of-sample check**: 10 real approved TTB labels from `samples/real` (not the bundled demo set) through `/api/check` on the shipped async path — measured, with the raw run committed, in [latency-real-10.json](latency-real-10.json). (An earlier version of this row quoted median 5.1s / max 5.6s from a 2026-08-13 session with no committed artifact; the committed run replaces it.) Four of the ten returned a provisional `fail_wording` that the background second reading downgraded to review, which is what the headline's new "Double-checking the government warning" state exists to report honestly
- **P2 — MET** Batch 200–300 first-class — batch review page: CSV+files dropzone, loud pairing, filters/search/pagination, detail panel, sample batch
- **P3 — MET, now through the real UI** 250-label batch, two independent runs on the deployed app. Server path: **135s, 250/250 ok, 0 rate-limited, 0 errors** ([measured-performance.json](measured-performance.json)) — but that harness posts to `/api/check` from node and skips everything the browser does per row, which an audit rightly flagged as an unevidenced gap in a first-class requirement. Closed by driving 250 files through the **batch UI itself** — client-side deskew per image, 250 object URLs, filename pairing, streaming table: **146.5s, 250/250 completed, 0 errors, 0 rate-limited, 0 pairing issues** ([batch-ui-250.json](batch-ui-250.json)). Two honest notes on that run: the wall-clock is an upper bound (the browser pane was not composited throughout, which throttles timers — the counts are fetch-driven and unaffected), and **all 250 rows landed in Needs review**, because past 60 rows the bold pass is opt-in and a row whose bold was never examined must not show a green tick. That is deliberate and documented, but it does mean the brief's headline 250-label case starts as "review everything" until the agent clicks *Check bold type*. **Re-measured 2026-08-13 after this round's UI changes** ([batch-72-optin.json](batch-72-optin.json)), because the 250-row evidence predates them: 72 labels (past the 60-row opt-in point) checked through the UI in **56.8s, 0 errors, 0 rate-limited, 0 pairing issues**; clicking *Check bold type* then resolved **39 of 56 eligible rows by measurement**, leaving 17 for a human glance, settling in ~107s. So the "review everything" start is one click from "review seventeen". **The full 250 was then re-run on the deployed app, 2026-08-14** ([batch-ui-250-postfix.json](batch-ui-250-postfix.json)): **250/250 completed, 0 errors, 0 rate-limited, 0 pairing issues**, 190 clean / 40 needs-review / 20 warning-failure, counts read from the exported report rather than the table so they are exact. The app reported 139.1s against the earlier run's 146.5s — both measured with the browser pane hidden, so both are active processing time rather than foregrounded wall clock, and they are recorded as approximate for that reason. (A caution about mid-pass reads comes from the *72-row* run, [batch-72-optin.json](batch-72-optin.json), not this one: an early read there at 10s showed 49 matched and was optimistic by 16 rows — a sentence this document previously attached to the 250-row run by mistake.) **Process unified 2026-08-14, and re-measured on the deployed unified build with the pane VISIBLE** ([batch-ui-250-unified.json](batch-ui-250-unified.json)): the opt-in *Check bold type* chip is gone — the bold pass always runs, bands arrive with each row's verdict from the same call a single check uses, and a clean row still being measured sits in a grey *Checking bold…* state instead of inflating Need review. The run: **250/250 completed in 158.7s real wall clock, 0 errors, 0 rate-limited, 0 pairing issues**, and the bold measurement settled at ~150s — before the check pass finished, so the separate bold-pass wait no longer exists. Settled buckets: 112 machine-cleared, 138 with genuine review work (59 of them one-hover bold glances in the strip). The earlier runs above predate the change, describe the opt-in flow they measured, and carry pane-hidden timings.

### UX
- **U1 — MET** Non-technical 50+ usable — 3-click demo verified in browser: sample → rendered verdict (single) and sample batch → triage, zero downloads/instructions; UX cold-read at final gate. Evidence rows are clickable across their whole width, not just their text: the target was measured at 73–75% of the row, so clicking a status chip or the empty space did nothing and gave no reason why. A container handler now takes the click and ignores anything originating in a real control, so the Accept / Reject pair keeps its own presses (verified: chip click highlights, Accept records without toggling the highlight, *Not provided* rows stay inert, keyboard focus and activation unchanged)
- **U2 — MET** Loud human-readable errors — type/size guards, refusal/timeout/429 copy ([lib/vision/extract.ts](../lib/vision/extract.ts) `failureMessage`), not-a-label card, CSV-format and pairing errors
- **U3 — MET** Triage 250 without drowning — count-carrying filter chips (All / Matched / Need review / Checking bold / Not required). *Need review* contains only rows the machine flagged; a clean row whose bold measurement is still running sits under the temporary grey *Checking bold* chip ([lib/batchTriage.ts](../lib/batchTriage.ts), 14 unit tests) — before 2026-08-14 those rows counted under Need review, which on a 250-row batch meant the page opened with **all 250 rows demanding review**, a wall of amber the owner correctly called a waste. A green tick still always means finished: measuring rows are grey, never green, one-click **Need review** filter + search, master-detail table (row click opens the evidence panel with an Audit trail tab; flagged fields and the bold glance are decided in place on their own rows, exactly as on the single-check page, and the panel footer carries an **Accept label** / **Reject label** ruling that outranks machine triage; Review next steps through), **Download report** (CSV with `agent_review` and `bold_check` columns), refresh guard; verified in browser on sample batch
- **U4 — MET** Dave's "don't make my life harder" = false-rejection aversion, designed in — tri-state `unreadable` ≠ `missing` (glare → "check manually", never a fail); second-reading confirmation on warning failures, plus four gates added after large-scale measurement — deviation-agreement (two readings must agree *which* word differs), legibility (no word-for-word claim on text that could not be read), disputed-absence, and statement-boundary trimming — measured **42 false rejections across 1,360 synthetic degradations (7.5% of compliant samples)**, concentrated in tear/occlusion where the warning is physically destroyed ([robustness-matrix.json](robustness-matrix.json)); on **156 scored real approved TTB labels** the tool's own false-rejection rate is **4 of 156 (2.6%)** ([real-labels.json](real-labels.json), causes in [real-labels-causes.json](real-labels-causes.json)): all 40 `fail_missing` verdicts were verified correct by direct inspection on contact sheets — front, neck or EU-market labels carrying no US warning — recorded per-label in [samples/real/manifest.json](../samples/real/manifest.json) (`has_warning: false` + `excluded_reason`). Those 40 are therefore excluded from the scored set, which is why the denominator is 156 and not 196, and of the 22 remaining flags **18 are labels whose printed text genuinely departs from 27 CFR 16.21** — square brackets for parentheses, a period for a comma, a dropped "the" — confirmed by a second independent reading and spot-checked by eye. Only 4 are the tool reading the wrong region of a crowded label; verdict vocabulary surfaces, never auto-rejects; case/punct differences read "Match — formatting differs" ([approach.md](approach.md) §perception/verdict, [degraded-fidelity.json](degraded-fidelity.json))

## Soft requirements (writeup lines mandatory)
- **N1 — MET on the stretch goal as written; extended well past it** — the brief asks to "tolerate imperfect photos (weird angles, bad lighting, glare)". Scored on exactly those three: **544 images, 224 compliant, 516 safe (94.9%), ZERO false rejections** ([robustness-matrix.json](robustness-matrix.json)). The claim is robust to how "bad lighting" is read: refuse to count `shadow` as bad lighting and it is **still zero false rejections**, on 196 compliant samples. All **28** violations not caught inside these families are bold-only defects measured at the raw advisory layer (see C9 — the shipped gate sends those to amber); **text-based violations are caught 256 of 256, 100%**. Two honest qualifications. First, "MET" is an assessment against a rubric written here, and a stretch goal is not a status the brief confers. Second, and more substantive: these 544 are *simulated* optics — degradations applied to rendered labels. Genuine photographs of physical bottles appear only in the real COLA corpus (curved labels with paper texture, foil stamps shot at an angle with real shadow), and that corpus by construction contains **no degraded capture** — nobody submits a badly-shot photo to a regulator. So "tolerates the named distortions" is supported, and "validated on photographs taken under those distortions" is not; the two corpora cover different halves and the seam between them is the honest gap. Testing then went beyond the ask — occlusion, tearing, creasing, curvature, sensor noise, colour cast and heavy downscaling — and **every one of the 42 false rejections in the full matrix comes from those extra conditions**, none from the three the brief names. Full detail — **1,360 synthetic degradations** (34 scoreable labels × 40 conditions: blur, angle, rotation, low light, overexposure, JPEG, downscale, glare, shadow, crease, curvature, tear, occlusion, sensor noise, colour cast, combined): **1,257/1,360 safe (92.4%), 42 false rejections (7.5% of 560 compliant samples), 61 violations not caught (7.6% of 800 violation samples)** ([robustness-matrix.json](robustness-matrix.json)). False rejections concentrate in physical destruction — occlusion (20) and tear (18) — where part of the warning is genuinely gone. Of the 61 not caught, **56 are the bold advisory**; re-scored through the shipped stroke-width gate that number falls to **3 of 160 (1.9%)** ([bold-gate-rescore.json](bold-gate-rescore.json)) — the matrix reads the raw server advisory, a layer the UI never shows. Also measured against **200 harvested real TTB COLA labels, 156 of them scored** ([real-labels.json](real-labels.json)). The COLA corpus mixes flat print files with genuine photographs (curved labels on bottles, angled foil stamps with real shadow), so real optics are represented; what it structurally cannot contain is **degraded capture** — nobody submits a torn or obscured photo to a regulator, which is why the synthetic matrix carries that axis. Real photographs of *damaged* labels remain the honest gap — [approach.md](approach.md) §limitations item 4
- **N2 — MET** Blocked-network path — approach doc §deployment (Bedrock GovCloud / Azure gateway / on-prem VLM)
- **N3 — MET** Test labels — 35 ground-truthed labels: a 20-label adversarial core (5 defect types — word swap, word drop, punctuation drift, title-case prefix, non-bold prefix — across 4 templates: bourbon, can/beer, gin, wine) plus 15 others (clean matches, case/punctuation differences, missing and small warnings, all-caps body, printed injection text, and the 6 extra batch labels) plus 200 harvested real TTB COLA labels (156 scored) incl. adversarial + injection ([samples/](../samples)), AI-encouraged generation honored via HTML-render pipeline
